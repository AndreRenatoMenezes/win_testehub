1. Introducao

1.1 Objetivo

O Hardware Test Hub e um framework de validacao de hardware projetado para avaliar o desempenho e a estabilidade dos principais componentes de uma maquina Windows: processador, memoria, disco, rede e ciclo de boot/shutdown. Os testes simulam cenarios de uso intensivo e coletam metricas objetivas para determinar se o equipamento atende aos padroes operacionais esperados.

1.2 Escopo

O que e testadoO que NAO e testado
Desempenho de CPU e memoria sob estressePerifericos (teclado, mouse, webcam)
Velocidade de leitura/escrita do discoGPU / desempenho grafico
Velocidade de rede (download, upload, latencia)Bateria (autonomia / ciclos de carga)
Tempo de boot e shutdown do WindowsConformidade de software (licenciamento)

1.3 Como Usar Este Documento para Auditoria Gestao

Para auditar uma execucao:

  1. Identifique o cenario em Traces/ (pasta com nome, hostname e data)
  2. Abra o _relatorio.html para ver o resumo de resultados
  3. Compare os procedimentos descritos neste documento com as evidencias coletadas
  4. Verifique a cadeia de custodia usando o _state.json (secao 8)

2.2 Sistema de Cenarios

Cada sessao de testes pertence a um cenario — uma unidade logica que agrupa execucoes (runs) e suas evidencias. Cenarios permitem testar uma maquina ao longo de varios dias, re-executar testes falhos e gerar relatorios consolidados.

Formato de identificacao: {NomeDoCenario}_{Hostname}_{Data}

2.3 Contrato de Exit Codes Tecnico

Exit CodeStatusRegra
0PASSTeste concluiu com sucesso e todas as verificacoes passaram
≠ 0FAILTeste encontrou falha, erro ou nao completou corretamente

Implementacao: Python usa sys.exit(0) / sys.exit(1). PowerShell usa exit 0 / exit 1.

2.4 Variaveis de Ambiente Injetadas Tecnico

VariavelDescricaoExemplo
HUB_EVIDENCE_DIRPasta de evidencias do testeTraces/Cenario_PC01/2_disco/
HUB_TRACE_DIRIdentica a HUB_EVIDENCE_DIR(mesmo acima)
HUB_TRACE_ROOTPasta raiz do cenarioTraces/Cenario_PC01/
Regra Testes nunca devem salvar arquivos na pasta raiz do projeto. Toda evidencia deve ser direcionada para HUB_EVIDENCE_DIR.

3. Fase de Setup — Preparacao do Ambiente

3.1 Objetivo

Padronizar a configuracao da maquina antes dos testes, garantindo que todos os equipamentos sao testados em condicoes equivalentes.

3.2 Scripts de Preparacao

#ScriptDescricaoJustificativa
1captura_infos_pcColeta informacoes do sistemaRegistro de identidade da maquina
2opcoes_energiaPlano de energia alto desempenhoEvita throttling e suspensao

4install_pythonInstala Python 3Pre-requisito dos testes
5install_py_dependenciesCria venv e instala pacotesIsolamento de dependencias
6pausa_WinUpdatePausa Windows UpdateEvita interferencia nos testes

8enable_diagnosticsHabilita diagnosticos do WindowsNecessario para teste de boot

3.3 Justificativa da Padronizacao Gestao

Por que padronizar? Sem a Fase de Setup, diferencas de configuracao entre maquinas (plano de energia, atualizacoes em andamento, falta de dependencias) poderiam gerar variacoes nos resultados que nao refletem o desempenho real do hardware. A padronizacao garante que diferencas nos resultados sao atribuiveis ao hardware, nao a configuracao de software.

Modulo 1 — CPU e Memoria

4.1 Objetivo

Avaliar o desempenho e a estabilidade do processador e da memoria sob carga sustentada, simulando um cenario de uso intensivo prolongado.

4.2 Ferramentas Utilizadas

  • Microsoft Edge via Selenium WebDriver — geracao de carga de CPU
  • Windows Performance Analyzer (WPA) — perfilamento do sistema
  • psutil — monitoramento de metricas de CPU em tempo real

4.5 Criterio de Aprovacao

CondicaoResultado
Todos os 5 ciclos completados sem erroPASS (exit code 0)
Qualquer ciclo falha, crash ou timeoutFAIL (exit code 1)

4.6 O que um FAIL Significa Gestao

Falha no teste de CPU/Memoria Indica que o processador ou memoria nao conseguiram sustentar carga por 5 ciclos. Possiveis causas: superaquecimento (thermal throttling), instabilidade de memoria, incompatibilidade de driver/firmware, ou recurso insuficiente. Acao: Investigar logs em Logs/run_*.log e verificar hardware.
Interrupcao segura O operador pode pressionar Ctrl+Q a qualquer momento para interromper o teste de forma controlada.

  • Servidor de speedtest interno (URL em config.local.json → SpeedtestUrl, nao versionada) — ponto de medicao padronizado

4Captura de screenshot como evidencia~2s
5Extracao de metricas via regex~1s
6Repeticao por 5 afericoes~6 min total
7Geracao de CSV consolidado~2s

Modulo 4 — Boot e Shutdown

7.1 Objetivo

Avaliar o tempo de inicializacao e desligamento do Windows atraves de multiplos ciclos de reinicializacao, identificando degradacoes e gargalos no processo de boot.

7.2 Ferramentas Utilizadas

  • Agendador de Tarefas do Windows — automatizacao das reinicializacoes
  • Event Log de Diagnosticos (Microsoft-Windows-Diagnostics-Performance/Operational)
  • PowerShell (boot_shutdown_duration.ps1) — analise dos eventos

7.3 Procedimento

Etapa 1 — Ciclos de Reinicializacao (automatico)

CicloAcao
1Cria tarefa agendada, agenda shutdown em 5 minutos
2Maquina reinicia → script executa via ONLOGON → aguarda 5 min → reinicia
3(repete)
4(repete)
5(repete)
6Ultimo ciclo → executa analise e limpa tarefa agendada

Tempo total estimado: ~30-40 minutos

Atencao Durante os ciclos, a maquina reinicia automaticamente 5 vezes. Nao interrompa o processo. O hub retoma automaticamente apos cada reinicializacao.

Etapa 2 — Analise de Eventos

EventoIDO que mede
Boot completo100MainPathBootTime e BootPostBootTime
Shutdown completo200Tempo total de desligamento
Degradacao de boot101-110Drivers, servicos e apps que atrasaram o boot
Atraso no shutdown201-203Processos que atrasaram o desligamento

7.4 Metricas Coletadas

MetricaUnidadeDescricao
MainPathBootTimemilissegundosTempo do caminho principal de boot
BootPostBootTimemilissegundosTempo de atividades pos-boot
ShutdownDurationmilissegundosTempo total de desligamento
Eventos de degradacaotextoCausas de lentidao detalhadas

7.5 Criterios de Avaliacao

Boot:

< 30s Normal
30s–60s Aviso
> 60s Critico

Shutdown:

< 20s Normal
20s–60s Aviso
> 60s Critico

7.6 Criterio de Aprovacao

CondicaoResultado
Nenhum evento critico nos boots do diaPASS
Pelo menos um evento criticoFAIL
Nota Eventos de "aviso" (warning) sao registrados no relatorio mas nao causam FAIL. Apenas eventos criticos reprovam o teste.

7.7 Impacto de Degradacao Gestao

CenarioImpacto estimado
Boot > 60s em 100 maquinas, 1 reinicio/dia~1.7 horas/dia perdidas pela operacao
Boot > 60s com 5 reinicios/semana~8.3 horas/semana por 100 maquinas

Causas comuns: drivers desatualizados, servicos de terceiros (antivirus, agentes), aplicativos no startup, disco lento.

10. Glossario

TermoDefinicao
AfericaoUma medicao individual dentro de um teste (ex: cada uma das 5 medicoes de velocidade de rede)
BateriaUm ciclo completo de operacoes dentro de um teste (ex: cada uma das 10 baterias de leitura/escrita)
CenarioSessao de testes associada a uma maquina e data, agrupando runs e evidencias
CooldownPeriodo de espera entre ciclos de estresse para a CPU retornar ao estado ocioso
DiskSPDFerramenta de benchmarking de disco da Microsoft
EvidenciaArquivo gerado por um teste que comprova o resultado (CSV, screenshot, log)
Exit CodeCodigo numerico retornado por um processo. 0 = sucesso, ≠ 0 = falha
HubO orquestrador (hub.ps1) que gerencia a execucao dos testes
JitterVariacao na latencia de rede entre pacotes consecutivos
OverlayJanela visual transparente exibida durante a execucao de um teste
PingTempo de ida e volta de um pacote de rede (latencia)
RunUma execucao do hub. Um cenario pode ter multiplas runs
SetupFase de preparacao do ambiente (instalacao e configuracoes)
StateArquivo _state.json que rastreia o estado de um cenario
ThrottlingReducao automatica de desempenho do processador por superaquecimento
ThroughputQuantidade de dados transferidos por unidade de tempo (MB/s ou Mbps)
TraceConjunto de evidencias de uma execucao
WPAWindows Performance Analyzer — ferramenta de analise de desempenho do Windows
